# Setup guide

Owner: LUNASaan Documentation Team
Last updated: 2026-10-21

How to set up a Databricks workspace to run LUNASaan? from an empty catalog to a dashboard. To run without Databricks, read [reproducibility](reproducibility.md) instead.

Status date: 2026-10-21. Items marked **confirm** depend on your workspace.

---

## 1. What you need

| Item | Value in the team workspace |
|---|---|
| Databricks workspace with Unity Catalog and serverless compute | Personal workspace (the FTW org workspace could not reach the external volume) |
| Catalog | `public_health` |
| Landing Volume | `/Volumes/workspace/default/ftw-b12-de/groups/g5_landing` (**confirm** for your workspace) |
| SQL warehouse | Any serverless SQL warehouse; its id goes in the bundle variable `warehouse_id`. Keep a short auto-stop (D-59) |
| Databricks CLI | Authenticated to the workspace (`databricks auth login --host <workspace-url>`) |
| The repository | Cloned locally, branch `dev` |
| Source files | Open sources downloaded from their publishers; restricted files from the team's FOI requests (never in the repository) |

## 2. One-time setup

1. **Create the catalog** `public_health` if it doesn't exist, and the landing Volume.
2. **Set the landing paths** if your Volume differs from the team's: `landing_root` in each `config/sources_<domain>.yaml`, `psgc.landing_path` and `hdx_phl_admin.landing_path` in `sources_geography.yaml`, and the reference CSV paths in each silver `*_00_reference.sql`.
3. **Set the bundle variable** `warehouse_id` in `databricks.yml` (or pass `--var warehouse_id=<id>`).
4. **Deploy:**

```bash
databricks bundle validate -t dev
databricks bundle deploy -t dev
```

This deploys two jobs: the pipeline (`resources/ph_public_health_job.yml`) and the setup job (`ph_public_health_setup_job.yml`). The pipeline's first task runs the setup job, which creates the schemas (`bronze`, `silver`, `gold`, `quality`), `bronze.ingestion_metadata` and the quality tables, and seeds `quality.check_registry` (`quality_registry_seed.sql`). It only creates or adds what is missing, so it is safe on every run.

## 3. Land the data

| What | Where | How |
|---|---|---|
| File sources | `<landing_root>/<domain>/<source>/`, file names as in each YAML entry | Upload the files. Never edit a landed file; a new release is a new file |
| Restricted files | `<landing_root>/<domain>/restricted/` | Upload; never commit. Or set their YAML entries to `enabled: false` ([data request log](../02-data/data-request-log.md), section 5) |
| PSGC snapshot | `<landing_root>/geography/psgc_api/raw/version=<v>/run_id=<id>/` | Run the PSGC landing job in `src/01_ingestion` by hand (not in the pipeline job) |
| HDX boundaries | `<landing_root>/admin_boundaries/_runs/<run_id>/` | Run the HDX ingestion notebook in `src/01_ingestion` by hand; it writes `handoff.json` |
| Reference CSVs | `<landing_root>/reference/<domain>/` | Copy from `config/reference/<domain>/`. They are generated by `builders/` and reviewed ([reference maps](../04-pipeline/silver/reference-maps.md)) |

Check what bronze would load without writing anything:

```bash
python src/02_bronze/run_bronze.py --plan true
```

On Databricks, run the same as a notebook cell or a one-off Python task.

The HDX ingestion is a manual dependency. Use only a completed run folder with its `handoff.json`; the pipeline does not silently fall back to an older boundary run. See [troubleshooting](troubleshooting.md) if the handoff is incomplete.

## 4. Run the pipeline

Runs are started by hand (D-59): whoever lands new data starts the job.

```bash
databricks bundle run ph_public_health_pipeline -t dev
```

Or press **Run now** on the job in the workspace. The job runs setup → bronze (+ bronze QC) → preload gate → silver (+ silver QC) → cross-domain QC → gold → gold QC → registry check (`qc_registry`), and stops on the first failed gate or FAIL check. A first run on an empty workspace loads every file; later runs load only new or changed files.

## 5. Check the run

```sql
-- every QC script's last run
SELECT layer, script_name, status, checks_total, checks_fail, checks_warn, started_at
FROM public_health.quality.run_log
QUALIFY row_number() OVER (PARTITION BY script_name ORDER BY started_at DESC) = 1
ORDER BY layer, script_name;

-- anything that is not PASS
SELECT layer, table_name, source_key, check_id, status, detail
FROM public_health.quality.v_open_issues
ORDER BY status, layer, table_name;

-- latest build of every silver and gold table
SELECT target_table, status, row_count, finished_at
FROM public_health.quality.v_latest_build
ORDER BY target_table;
```

Expected: no FAIL; the WARNs listed on the [bronze](../04-pipeline/bronze/bronze-quality-checks.md) and [silver](../04-pipeline/silver/silver-quality-checks.md) quality pages.

## 6. Dashboard

The dashboard (Databricks AI/BI and Genie) reads the gold marts and default views in `public_health.gold`. Point it at your warehouse; see the [dashboard guide](../05-dashboard/dashboard-guide.md). The job has an optional `dashboard_refresh` task, commented out (to-do 10).

## 7. When something fails

Start with the [runbook](runbook.md): it says how to read the message, where to look, and how to rerun safely. Common cases: [troubleshooting](troubleshooting.md).
